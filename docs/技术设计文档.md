## 1. 总体架构与技术选型

### 1.1 技术选型

| 层 | 选型 | 选型理由（需求导向） |
|---|---|---|
| 前端 | React + Vite + TypeScript | 轻量主流，6 个页面够用 |
| 后端 | FastAPI | 原生 SSE、异步、Python AI 生态标准 |
| Agent 引擎 | LangGraph | checkpoint + 状态机，精确表达多 Agent 控制流 |
| 数据库 | PostgreSQL | 结构化数据 + JSONB + **pgvector 扩展**（一个库统一结构化+向量） |
| 向量检索 | pgvector（PG 扩展） | 数据量小（FAQ/故障说明几百~几千条），够用，省一个独立服务 |
| 异步 | 暂不上 Celery | FastAPI 异步 + SSE 已够；架构预留任务执行抽象，未来需要时无缝接入 |

> **关键选型决策**：不用 Milvus（数据量小，pgvector 足够）、不用 Celery（无分钟级长任务）。原则是"该轻量的轻量、该重型的重型"。

### 1.2 系统分层

```
┌─────────────────────────────────────────┐
│  前端（React + Vite）                     │
│  客户端3页 + 管理端3页                     │

               │ REST + SSE（流式）
┌──────────────▼──────────────────────────┐
│  后端（FastAPI）                          │
│  接口层：对话/下单/订单/审批/知识库 API     │
│  编排层：LangGraph 多 Agent 编排           │
│  工具层：查政策/查订单/RAG检索/查规格       │
└──────────────┬──────────────────────────┘
               │

│  数据层                                   │
│  PostgreSQL（结构化 + pgvector 向量 + checkpoint）│
└─────────────────────────────────────────┘
```

## 2. Agent 体系设计

### 2.1 总览（3 Agent + 1 分流器）

| 角色 | 职责 | 工具 | 形态 |
|---|---|---|---|
| **① 分流器（router）** | 判断意图，路由到简单/复杂/投诉 | 无（纯分类） | 节点（轻量模型） |
| **② 客服 Agent** | 简单问答（FAQ/售前/简单故障咨询） | FAQ检索、故障检索、商品规格、商品列表 | 子图（ReAct 循环） |
| **③ 技术诊断节点** | 判断故障原因、是否同一故障 | 故障检索 | 节点（查证+结构化） |
| **④ 售后 Agent** | 政策判断 + 订单核实 | 政策查询、订单查询 | 节点（查证+结构化） |
| **⑤ 决策 Agent** | 交叉核验 + 结论 + 置信度 + 安抚 | 无（纯推理综合） | 节点（结构化） |

**设计原则**：
- 不用独立质检 Agent——防幻觉靠**结构化约束**（政策结论来自结构化查询，非 LLM 编造），不靠事后审查。
- 模型分层：分流用轻量模型（分类是简单任务，调用次数最多），回答用强模型。
- Agent 有两种实现形态：客服 Agent 是「子图」（需要 ReAct 循环），技术诊断/售后/决策是「节点」（一次查证 + 结构化输出）。两者都是独立 Agent（各有 LLM + 工具 + prompt），只是形态不同。

### 2.2 各 Agent 职责明细

**① 分流器**：输入完整对话历史，输出 `simple/complex/complaint` + 置信度 + 风险信号。见第 3 节。

**② 客服 Agent**（简单问答，子图）：
- 回答 FAQ、产品咨询、按预算/定位推荐商品
- 用 ReAct 循环（agent ⇄ tools），输出文本

**③ 技术诊断节点**（技术诊断）：
- 查故障说明，判断故障原因、是否同一故障
- 输出结构化 `TechResult`

**④ 售后 Agent**（政策 + 订单）：
- 查三包政策字段，判断政策是否适用
- 查订单 + 维修记录，核实购买时间、维修次数
- 输出结构化 `AftersaleResult`

**⑤ 决策 Agent**（交叉核验）：
- 读 `TechResult` + `AftersaleResult`，做字段级交叉核验
- 输出 `FinalDecision`（结论 + 置信度 + 政策依据 + 安抚话术）

## 3. 意图识别与分流

### 3.1 分类类别（3 类）

| 分类 | 路由目标 | 说明 |
|---|---|---|
| `simple` | 客服 Agent | FAQ、售前、简单故障咨询 |
| `complex` | 并行协同（技术诊断∥售后） | 涉及退换货判断，需技术+政策+订单 |
| `complaint` | 转人工 | 高风险情绪/投诉意图 |

### 3.2 三层实现

```python
# 第 1 层：规则快筛（零 LLM 调用）
HIGH_RISK_KEYWORDS = ["投诉", "曝光", "12315", "消协", "差评", "退一赔三"]
REFUND_KEYWORDS   = ["退款", "退货", "换货", "换新", "赔偿"]

def rule_triage(text) -> str | None:
    if any(k in text for k in HIGH_RISK_KEYWORDS):
        return "complaint"
    if any(k in text for k in REFUND_KEYWORDS):
        return "complex"
    return None   # 拿不准，交给 LLM

# 第 2 层：轻量模型结构化分类
class IntentClassification(BaseModel):
    intent: Literal["simple", "complex", "complaint"]
    confidence: float = Field(ge=0, le=1)
    risk_signals: list[str] = Field(description="命中的风险信号")
    reasoning: str = Field(description="为什么这么分")

# 第 3 层：置信度兜底
def route(intent: IntentClassification) -> str:
    if intent.intent == "complaint":
        return "escalate"                 # 投诉永不自动处理
    if intent.confidence < 0.7:
        return "complex_pipeline"         # 低置信 → 复杂流程（稳妥）
    return intent.intent
```

### 3.3 简单 vs 复杂的边界判据（写进分流器 prompt）

| 信号 | 说明 | 例子 |
|---|---|---|
| `refund_intent` | 退款/退货/换货诉求 | "修两次了要换货" |
| `policy_dependent` | 答案依赖三包政策 | "过保了还能修吗" |
| `multi_domain` | 跨技术+政策+订单多域 | "蓝屏修两次，三包期内能换吗" |
| `anger` | 情绪/威胁 | "太差了我要投诉" |

**判据：命中任意一个 → complex/complaint；一个都没命中 → simple。**

### 3.4 评测（召回率优先）

```python
complaint_recall      # 投诉召回率 = 100%（漏一个投诉不可接受）
complex_recall        # 复杂售后召回率 > 95%
fast_path_precision   # 快速通道"真简单"比例 > 90%
```

## 4. 复杂售后并行协同 + 交叉核验

### 4.1 并行实现（LangGraph 并行边）

```
router ──┬──▶ tech（技术诊断）──┐
         │                     ├──▶ decision（交叉核验）
         └──▶ aftersale（政策+订单）─┘
```

两个节点无依赖，用 Send API 并行 fan-out。**各写各的 state 字段，避免 reducer 冲突**：

```python
def route(state):
    if state["intent"] == "complex":
        return [Send("tech", state), Send("aftersale", state)]  # 并行 fan-out
    ...

builder.add_edge("tech", "decision")
builder.add_edge("aftersale", "decision")  # 两个都完成后自动汇聚
```

> ⚠️ Send 的第二个参数是目标节点接收的**完整 state**（不是"额外更新"），传空 dict 会导致节点读不到 messages，必须传完整 state。

### 4.2 结构化输出（交叉核验的基础）

```python
class TechResult(BaseModel):
    fault: str              # 故障现象
    same_fault: bool        # 是否同一故障（"修两次"场景关键）
    cause: str              # 可能原因
    confidence: float

class AftersaleResult(BaseModel):
    order_valid: bool
    in_warranty: bool       # 三包期内？
    repair_count: int       # 维修次数
    policy_applicable: bool # 政策是否适用
    policy_ref: str         # ⭐ 政策条款引用（来自结构化查询，非 LLM 编造）
    confidence: float
```

### 4.3 交叉核验（决策 Agent 字段比对）

```python
class FinalDecision(BaseModel):
    conclusion: Literal["换货", "退货", "维修", "不满足", "转人工"]
    confidence: float
    reasoning: str          # 交叉核验推理
    policy_ref: str         # 最终政策依据
    comfort_msg: str        # 安抚话术
```

**交叉核验逻辑**：决策 Agent 读 `TechResult` + `AftersaleResult`，做字段级比对：

```
same_fault=True 且 repair_count>=2 且 policy_applicable=True → 换货
same_fault=False 但政策要求"同一故障" → 不满足换货，只能维修
```

**字段比对的价值**：矛盾是 `same_fault=False` vs `政策要求 same_fault=True` 的字段冲突，一眼可见，不需要 LLM 读两段文本"感觉"。

### 4.4 冲突处理

| 情况 | 处理 |
|---|---|
| 矛盾能由字段比对解决 | 决策 Agent 按字段逻辑输出正确结论 |
| 两路高置信但硬冲突 | 决策置信度降低 → 转人工 |
| 某路查证失败/超时 | 基于另一路给降级结论 + 标注"某部分未核实" |

## 5. 知识库分源检索 + 工具设计

### 5.1 知识库分类（两类，两种查法）

| 类别 | 内容 | 查法 |
|---|---|---|
| 结构化（字段明确） | 三包政策、商品规格、订单、维修记录 | **精确查询 + 规则判断** |
| 非结构化（开放问答） | FAQ、故障说明 | **pgvector RAG 召回** |

> 政策不能用 RAG——语义近似对政策判断是灾难（"修2次"≠"修3次"）。

### 5.2 工具清单（6 个）

| 工具 | 归属 | 类型 |
|---|---|---|
| `search_faq` | 客服 | RAG 召回 |
| `search_troubleshooting` | 客服 | RAG 召回 |
| `get_product_spec` | 客服 | 结构化查询 |
| `list_products` | 客服 | 结构化查询 |
| `query_policy` | 售后 | 结构化查询 |
| `query_order` | 售后 | 结构化查询 |

### 5.3 结构化查询工具（以 query_policy 为例）

```python
class QueryPolicyInput(BaseModel):
    condition: Literal["warranty_period", "major_parts", "replace_condition", "return_condition"] = Field(
        description="要查询的政策项。warranty_period=保修期，major_parts=主要部件清单，"
                    "replace_condition=换货条件，return_condition=退货条件"
    )

def query_policy(condition) -> str:
    """查询微型计算机三包政策的指定条款。

    使用场景：需要判断用户的退换货诉求是否符合三包规定时。
    不要用于：查订单、维修记录（用 query_order）；查故障原因（用 search_troubleshooting）。

    返回：该政策项的精确字段值 + 政策出处原文。
    """
```

**设计要点**：enum 收窄政策项、输出是数据库取出的精确值（防幻觉）、description 划清边界。

### 5.4 RAG 检索工具（以 search_troubleshooting 为例）

```python
class SearchTroubleshootingInput(BaseModel):
    query: str = Field(description="故障描述，自然语言，如'蓝屏'、'充不进电'")
    product_model: Optional[str] = Field(default=None, description="可选，限定商品型号")

def search_troubleshooting(query, product_model=None) -> str:
    """检索笔记本故障说明知识库，返回最相关的故障知识。
    使用场景：用户描述故障现象，需找可能原因和排查方法时。
    返回：语义最相似的 top-3 故障说明（原因、排查方法、是否常见）。
    """
```

### 5.5 工具边界（防选错）

- `search_faq`（操作/使用） vs `search_troubleshooting`（坏了/异常）——入库时分库
- `get_product_spec`（已知型号查规格） vs `list_products`（按条件找型号）——单数 vs 复数

### 5.6 工具失败处理

| 失败 | 处理 |
|---|---|
| 参数校验失败 | 返回具体错误 + 正确格式，Agent 自愈 |
| 结构化查无结果 | 返回"查无 + 提示下一步" |
| RAG 召回为空 | 返回"未找到，建议转人工" |
| 数据库超时 | 代码层重试，不给模型看 |

## 6. HITL 与状态持久化

### 6.1 审批触发条件

| 触发 | HITL 形态 |
|---|---|
| 结论 ∈ {换货/退货/退款} | **审批**（坐席拍板） |
| 置信度低 / 投诉 / AI 无法处理 | **转人工**（接管，P1） |

### 6.2 审批完整流程

```python
def approval_node(state):
    approval = interrupt({                     # 暂停，持久化，等人操作
        "type": "approval",
        "conclusion": state["final_decision"].conclusion,
        "policy_ref": state["final_decision"].policy_ref,
        "comfort_msg": state["final_decision"].comfort_msg,
        "confidence": state["final_decision"].confidence,
    })
    return {"approval_result": approval}       # 坐席决策回来后继续
```

流程：`decision → approval_node(interrupt 暂停 + 写审批单表) → 坐席审批 → resume → 回复用户`

### 6.3 checkpoint 持久化（三大价值）

```python
from langgraph.checkpoint.postgres import PostgresSaver
checkpointer = PostgresSaver.from_conn_string(DB_URL)
graph = builder.compile(checkpointer=checkpointer)
```

| 价值 | 说明 |
|---|---|
| 中断恢复 | 服务重启后从 checkpoint 继续，审批等待不丢 |
| 时间旅行 | 回到任意历史状态排查 |
| HITL 基石 | interrupt 暂停时状态已持久化，resume 无缝恢复 |

### 6.4 审批单表（管理端数据枢纽）

interrupt 暂停时写 `approvals` 表，管理端读它展示（界面④"待审批详情页"就是这张表的一条记录）。

### 6.5 转人工接管（P1）

审批是"坐席给决策、Agent 继续"；接管是"坐席接管对话、Agent 退出"。机制同用 interrupt + checkpoint。

## 7. 状态设计与数据流

### 7.1 State 定义

```python
class CustomerServiceState(TypedDict):
    messages: Annotated[list, add_messages]     # 对话历史
    intent: str                                  # simple/complex/complaint
    intent_confidence: float
    risk_signals: list[str]
    tech_result: TechResult | None               # 客服 Agent 写（并行隔离）
    aftersale_result: AftersaleResult | None     # 售后 Agent 写（并行隔离）
    final_decision: FinalDecision | None
    approval_result: dict | None
    escalated: bool
    current_agent: str                           # 服务 SSE 推送
    step_count: int                              # 护栏
```

### 7.2 多轮对话机制（关键）

**每条消息 = 一次 graph.invoke()，checkpoint 用 thread_id 保持会话**：

```python
# 用户消息1 → invoke(thread_id="会话A") → router → simple → 客服回答 → END
# 用户消息2 → invoke(thread_id="会话A") → checkpoint 恢复历史 → router 重新分类 → complex → ...
```

- **每轮重新路由**（不是全局一次）：用户切换话题能正确重新分配
- **router 看完整历史**：理解"那个""这款"等指代，但重心是最后一条消息
- 边界情况（处理中发新消息）：MVP 用"排队等待"，中断重路由不做

### 7.3 完整数据流

```
START → router（分类）→
  ├─ simple → 客服 Agent → END
  ├─ complex → 并行[客服(技术)∥售后(政策+订单)] → 决策 → (审批?) → END
  └─ complaint → 转人工 → END
```

### 7.4 SSE 推送协议

每个节点更新 `current_agent`，通过 SSE 推给前端：

| current_agent | 用户看到 |
|---|---|
| `analyzing` | 正在分析您的问题 |
| `tech_agent` | [技术诊断 Agent] 正在查故障说明 |
| `aftersale_agent` | [售后 Agent] 正在查政策+订单 |
| `decision_agent` | 正在综合判断 |
| `pending_approval` | 等待人工审核 |

### 7.5 记忆设计（长短期记忆）

核心原则：**长期记忆靠结构化业务数据，不靠"存历史对话再向量召回"**。分四层：

| 记忆层 | 内容 | 实现 |
|---|---|---|
| 短期记忆 | 会话内对话历史 | State.messages + checkpoint + thread_id |
| 中期记忆 | 长会话历史摘要 | token 阈值 + LLM 摘要 + 保留最近 N 条 |
| 长期记忆（业务） | 订单、维修记录 | 结构化表，query_order 精确查询 |
| 长期记忆（画像，P2） | 用户偏好、历史意图 | user_profile 表（可选） |

**短期记忆**：每条消息一次 invoke，同 thread_id → checkpoint 自动恢复 messages，会话内上下文连贯。

**中期记忆（上下文压缩）**：当 messages token 超过阈值（70% 窗口），LLM 摘要旧消息、保留最近 5 条（借鉴 Customer-Agent 的 token 窗口 + 摘要）。

**长期记忆（核心）**：订单表 + 维修记录表就是用户的长期记忆，通过订单 Agent 的 `query_order` 精确查询。复杂售后需要的是精确数据（修了几次、过没过保），不是"用户上次说过什么"，所以结构化精确查询比向量召回历史对话更可靠——呼应本文档"结构化 vs 向量"的设计原则。

**用户画像（P2 可省）**：单一用户演示，画像可省；要加就是 user_profile 表（偏好、历史意图，从历史对话 LLM 提取）。

## 8. 数据库表结构（PostgreSQL）

### 8.1 业务表

```sql
-- 商品表（21 个笔记本）
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100),          -- 型号名
    brand VARCHAR(50),          -- 品牌
    category VARCHAR(50),       -- 定位：轻薄/游戏/全能/苹果/入门
    cpu VARCHAR(100),
    memory VARCHAR(50),
    storage VARCHAR(50),
    gpu VARCHAR(100),
    screen VARCHAR(50),
    weight VARCHAR(20),
    price DECIMAL(10,2)
);

-- 订单表（无登录，user 简化为固定值）
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    order_no VARCHAR(50) UNIQUE,
    product_id INT REFERENCES products(id),
    amount DECIMAL(10,2),
    created_at TIMESTAMP,
    status VARCHAR(20)          -- 已完成/退换货中/已退换
);

-- 维修记录表（构造数据，支撑"修两次"场景）
CREATE TABLE repairs (
    id SERIAL PRIMARY KEY,
    order_id INT REFERENCES orders(id),
    repair_date DATE,
    fault VARCHAR(200),
    status VARCHAR(20)
);
```

### 8.2 知识库表（结构化 + 向量双存）

```sql
-- 政策表（纯字段化，精确查询）
CREATE TABLE policies (
    id SERIAL PRIMARY KEY,
    category VARCHAR(50),        -- 微型计算机
    warranty_period VARCHAR(50), -- 整机保修期
    major_parts_period VARCHAR(50), -- 主要部件保修期
    major_parts TEXT,            -- 主要部件清单
    replace_condition TEXT,      -- 换货条件
    return_condition TEXT,       -- 退货条件
    source VARCHAR(200)          -- 政策出处
);

-- FAQ 表（文本 + 向量）
CREATE TABLE faqs (
    id SERIAL PRIMARY KEY,
    question TEXT,
    answer TEXT,
    question_embedding vector(1536)   -- pgvector，RAG 召回用
);

-- 故障说明表（文本 + 向量）
CREATE TABLE troubleshooting (
    id SERIAL PRIMARY KEY,
    product_model VARCHAR(100),
    fault TEXT,
    cause TEXT,
    solution TEXT,
    fault_embedding vector(1536)
);
```

### 8.3 HITL 表

```sql
CREATE TABLE approvals (
    id SERIAL PRIMARY KEY,
    thread_id VARCHAR(100),      -- 关联会话（resume 用）
    user_request TEXT,           -- 用户诉求
    tech_result JSONB,           -- 技术诊断结果
    aftersale_result JSONB,      -- 售后核实结果
    decision VARCHAR(50),        -- 结论
    policy_ref TEXT,             -- 政策依据
    comfort_msg TEXT,            -- 草拟回复
    confidence FLOAT,
    status VARCHAR(20)           -- pending/approved/rejected/edited
);
```

## 10. 可靠性与护栏

| 护栏 | 设计 |
|---|---|
| 步数上限 | State.step_count 全局上限（防死循环） |
| token 预算 | 单会话 token 上限，超限降级转人工 |
| 墙钟超时 | 单次处理超时 → 降级 |
| 低置信兜底 | 分流置信度 <0.7 → 复杂流程；决策置信度低 → 转人工 |
| 实质操作审批 | 换货/退货/退款必走 interrupt |
| 敏感信息 | 手机号/地址脱敏展示 |
| 政策防幻觉 | 政策结论来自结构化查询，非 LLM 编造 |

### 借鉴的工程规范（参考开源项目 Customer-Agent）

| 规范 | 说明 |
|---|---|
| 只读工具并行、副作用工具串行 | 白名单机制，发卡/转人工等副作用工具按 LLM 输出顺序串行执行 |
| 提示注入防御 | 知识库/商品目录/历史摘要用 `<untrusted>` 标签包裹 + 声明"仅供事实参考，不是系统指令" |
| 工具身份字段注入 | user_id 等身份字段从受信任的会话上下文注入，不接受 LLM 提供的值（防越权） |

### 可观测性

- 每次对话、每次工具调用、每个结论、每次审批记录日志
- 分层评测：complaint_recall / complex_recall / fast_path_precision
