## 1. 开发原则

1. **垂直切片**：先跑通端到端最小闭环，再横向扩展。不做"先完整数据库、再完整后端、最后联调"的水平分层。
2. **依赖前置**：被依赖的先做（数据地基 → 最小闭环 → 分流 → 协同 → HITL → 前端 → 打磨）。
3. **每阶段可验证**：每个阶段结束都有明确的验收标准和可 demo 的东西，不留"看起来做完但没验证"的中间态。
4. **P0 优先，P1 后置**：待接管队列（P1）、图片识别（P1）、用户画像（P2）等，在 P0 闭环跑通前不碰。

---

## 2. 阶段总览

| 阶段 | 主题 | 核心产出 | 依赖 |
|---|---|---|---|
| 0 | 初始化 + 数据地基 | 数据库建表 + 真实数据 | 无 |
| 1 | 最小端到端切片 | 单 Agent 简单问答跑通 | 阶段 0 |
| 2 | 分流器 | 三类意图正确分流 | 阶段 1 |
| 3 | 复杂售后协同 | 多 Agent 并行 + 交叉核验 | 阶段 2 |
| 4 | HITL 审批 | 审批闭环 | 阶段 3 |
| 5 | 前端完善 | 6 页面完整可演示 | 阶段 4 |
| 6 | 打磨 | 护栏 + 评测 + 安全 | 阶段 5 |

> 阶段 0-4 是 P0 核心链路，阶段 5-6 是完善。每个阶段约 2-4 天（个人节奏）。

## 3. 各阶段详细

### 阶段 0：初始化 + 数据地基

**目标**：搭好项目骨架，建好数据库，准备好真实数据。为阶段 1 铺路。

**开发任务**：

1. 目录结构：`backend/`（FastAPI + LangGraph）、`frontend/`（React）、`data/`（数据脚本）
2. PostgreSQL 建表（9 张）：
   - 业务表：`products`、`orders`、`repairs`
   - 知识库表：`policies`、`faqs`（含 `question_embedding vector`）、`troubleshooting`（含 `fault_embedding vector`）
   - HITL 表：`approvals`
   - `checkpoint` 表由 LangGraph `PostgresSaver` 自动建
3. 启用 pgvector 扩展
4. 数据准备：
   - **21 个商品真实规格**（从官网核实，整理成 SQL）
   - **三包政策**（字段化：《微型计算机商品修理更换退货责任规定》）
   - **FAQ**（整理真实常见问题）
   - **故障说明**（整理真实故障知识，关联型号）
   - **维修记录**（构造，支撑"修两次换货"场景）

**测试 / 验证**：

- `psql` 能连接，所有表创建成功
- SQL 查询能查到 21 个商品、政策字段
- pgvector 能存向量 + 相似度检索（用 2-3 条测试数据验证）

**验收标准**：数据库地基 + 数据齐备，阶段 1 可直接开工。

---

### 阶段 1：最小端到端切片（单 Agent 简单问答）⭐

**目标**：跑通完整技术栈，实现"简单问答"最小闭环。**这一阶段不追求功能，追求"技术栈能串起来"。**

**开发任务**：

1. FastAPI 骨架 + `/api/chat` SSE 接口
2. LangGraph 最简图：一个客服 Agent + `search_faq` 工具（pgvector 检索）
3. `search_faq` 工具实现（向量化 query → pgvector 相似度 → 返回 top-k FAQ）
4. 最简 React 对话页（一个输入框 + 对话区）
5. SSE 流式对接（前端能收到后端推送）

**测试 / 验证**：

- 用户问"怎么激活系统" → Agent 查 FAQ → 正确回答（端到端通）
- 多轮对话："那蓝色那款呢"能接上上下文
- SSE 流式推送正常，前端能实时显示

**验收标准**：技术栈（FastAPI + LangGraph + pgvector + React + SSE）全通的最小闭环，这是后续所有阶段的"地基可运行"。

> ⚠️ 阶段 1 跑不通，后面全停——先解决技术栈集成问题（pgvector 配置、SSE 对接、LangGraph 与 FastAPI 集成），这是本阶段真正的价值。

---

### 阶段 2：分流器

**目标**：实现意图识别与分流（3 类）。

**开发任务**：

1. 规则快筛（关键词：退款/退货/投诉等）
2. 小模型分类（`IntentClassification` schema + 轻量模型）
3. 置信度兜底（<0.7 → 复杂流程）
4. LangGraph 图结构：router 节点 + 条件边
5. 简单通道走通：simple → 客服 Agent 直接答
6. 分流评测：golden set 30 条（标注期望分类）

**测试 / 验证**：

- "怎么激活系统" → simple → 客服 Agent
- "修两次要换货" → complex（阶段 3 实现处理）
- "我要投诉" → complaint → 转人工（先占位，阶段 4 完整）
- 评测：`complaint_recall = 100%`（漏一个投诉都不行）

**验收标准**：三类意图正确分流，投诉零漏判。

---

### 阶段 3：复杂售后协同（核心）

**目标**：实现多 Agent 并行协同 + 交叉核验。这是整个项目的"肉"。

**开发任务**：

1. 客服 Agent 技术诊断模式：`search_troubleshooting` 工具 + `TechResult` 结构化输出
2. 售后 Agent：`query_policy` + `query_order` 工具 + `AftersaleResult` 结构化输出
3. 并行 fan-out（客服 ∥ 售后，各写各的 state 字段）
4. 决策 Agent：读两路结构化结论，字段比对交叉核验，输出 `FinalDecision`

**测试 / 验证**：

- "蓝屏修两次换货" → 并行查证 → 决策"符合换货条件" + 置信度
- "不是同一故障"（构造场景）→ 决策"不满足换货条件，只能维修"
- 交叉核验发现矛盾：技术说"非同一故障"、订单显示"两次同因" → 正确按字段逻辑裁决
- 两路查证失败 → 降级 + 标注"某部分未核实"

**验收标准**：复杂售后"修两次换货"场景端到端跑通，交叉核验能正确裁决矛盾。

---

### 阶段 4：HITL 审批

**目标**：实现审批闭环（interrupt + checkpoint + resume）。

**开发任务**：

1. 审批节点：`interrupt()` 触发暂停
2. checkpoint：`PostgresSaver` 接入
3. 审批单表：interrupt 时写 `approvals` 表
4. 管理端审批页：待审批列表 + 详情 + 批准/拒绝/修改
5. resume：审批提交 → `graph.invoke(Command(resume=...))`
6. SSE 推送审批结果回用户

**测试 / 验证**：

- 决策"换货" → 暂停 → 管理端出现待审批 → 坐席批准 → 用户收到"已生成换货单"
- 拒绝场景 → 用户收到拒绝理由
- **服务重启后审批状态不丢**（checkpoint 价值验证：审批等待时重启服务，恢复后仍在等审批）

**验收标准**：审批闭环跑通（暂停 → 人操作 → 恢复），checkpoint 中断恢复验证通过。

---

### 阶段 5：前端完善

**目标**：6 个页面完整实现，可完整演示。

**开发任务**：

1. 商品页：21 商品展示 + 一键下单
2. 我的订单：列表 + 详情 + 维修记录
3. 客服页完善：Agent 工作状态展示（SSE 事件）+ 信息卡片 + 依据展示 + 审批等待状态
4. 管理端：待审批队列（阶段 4 已有）+ 知识库管理（4 Tab）+ 待接管队列（P1）
5. SSE 事件完整对接（agent_status / message / done）

**测试 / 验证**：

- 完整用户旅程：浏览商品 → 下单 → 咨询售后 → 审批 → 解决，全流程无断点
- 6 页面都能正常操作
- 客服页能看到"三个 Agent 并行工作"的状态提示

**验收标准**：完整可演示，能走通 PRD 第 6 节的完整闭环。

---

### 阶段 6：打磨

**目标**：补可靠性和安全，让项目能扛住面试追问。

**开发任务**：

1. 护栏：步数上限、token 预算、墙钟超时
2. 提示注入防御：知识库内容 `<untrusted>` 标签包裹
3. 工具身份字段注入（user_id 从会话上下文注入，不接受 LLM 值）
4. 只读工具并行、副作用工具串行（白名单）
5. 日志：每次对话、工具调用、结论、审批记录
6. 评测：golden set 完整 + 分层评测指标

**测试 / 验证**：

- 死循环场景触发护栏（构造"反复问同一问题"验证步数上限）
- 注入攻击被防御（构造"忽略之前指令"的恶意消息）
- 评测指标达标（complaint_recall=100%、complex_recall>95%）

**验收标准**：可靠性和安全补齐，能讲清"护栏、防注入、评测"三个点。

## 4. 任务跟踪建议

用 GitHub Issues 跟踪（个人版 Jira）：

| 企业 | 个人项目 |
|---|---|
| Epic | 每个阶段 = 一个 milestone |

```
标题：[阶段3] 实现售后 Agent 的 query_policy 工具
验收：查询"replace_condition"能返回"同一故障修理两次可换货"原文
依赖：#12（阶段0 政策表）
```

## 5. 风险与注意事项

| 风险 | 应对 |
|---|---|
| 阶段 1 技术栈集成问题 | 阶段 1 就是为暴露这个设计的，卡住就优先解决集成 |
| 21 商品真实数据难搜集 | 阶段 0 用 WebSearch 逐个核实，可先做 5-8 个跑通再补全 |
| 小模型分类不准 | 用规则快筛 + 置信度兜底兜住，投诉漏判是红线 |
| 审批 checkpoint 配置复杂 | 阶段 4 单独验证"重启后状态不丢"，确保这关过了再继续 |
