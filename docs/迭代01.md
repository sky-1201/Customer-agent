## 1. 背景与目标

MVP 已跑通核心链路（分流 → 并行协同 → 交叉核验 → 人工审批），但从"演示 demo"到"能落地的产品"还有关键差距。本迭代计划的目标：**去掉所有演示期硬编码，补齐生产化的核心能力**。

核心差距清单：

| 维度 | 当前（demo） | 目标（生产） |
|---|---|---|
| 用户 | 单一用户，无登录 | 多用户隔离，各自数据 |
| 转人工 | 只有审批，无接管 | 坐席接管 + 实时对话 |
| 订单号 | 硬编码 O-001 | 动态获取 + 主动索取 |
| 审批界面 | 只看结论和置信度 | 展示完整判断理由 |
| 会话 | 前端 localStorage | 服务端会话管理 |

## 2. 迭代总览

## 3. 迭代 1：多用户隔离

### 3.1 产品需求（PRD）

**问题**：当前无登录，所有数据（订单、会话）是共享的，不符合真实产品。

**需求**：
1. 用户注册/登录
2. 登录后看到**自己的**订单、会话、审批
3. 数据隔离（安全红线：不能越权访问别人的数据）

### 3.2 数据模型变化

```sql
-- 1. 用户表（新）
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    username VARCHAR(50) UNIQUE NOT NULL,
    password_hash VARCHAR(200) NOT NULL,   -- 存哈希，绝不存明文
    created_at TIMESTAMP DEFAULT now()
);

-- 2. 订单表加 user_id
ALTER TABLE orders ADD COLUMN user_id INT REFERENCES users(id);

-- 3. 审批单加 user_id（或通过 thread_id 关联）
ALTER TABLE approvals ADD COLUMN user_id INT REFERENCES users(id);
```

### 3.3 鉴权方案

**选 JWT**（标准、无状态）：

| 接口 | 说明 |
|---|---|
| `POST /api/auth/register` | 注册（username + password） |
| `POST /api/auth/login` | 登录，返回 JWT token |
| 其他接口 | 加鉴权依赖，从 token 解析 user_id |

```python
# 密码哈希（绝不存明文）
from passlib.context import CryptContext
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")
password_hash = pwd_context.hash(password)

# 鉴权依赖（FastAPI Depends）
def get_current_user(token: str = Depends(oauth2_scheme)) -> int:
    payload = jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
    return payload["user_id"]
```

### 3.4 数据隔离（安全红线）

**核心原则**：所有查询按 `user_id` 过滤，这是安全底线，越权访问 = 事故。

```python
# 订单查询：只能查自己的
def list_orders(user_id: int) -> list[dict]:
    sql = "SELECT ... FROM orders WHERE user_id = %s"

# 审批查询：只能看自己的
def list_approvals(user_id: int) -> list[dict]:
    sql = "SELECT ... FROM approvals WHERE user_id = %s"

# 会话隔离：thread_id 编码 user_id
thread_id = f"user_{user_id}_session_{session_id}"
```

### 3.5 前端改动

- 登录/注册页（新）
- token 管理（localStorage 存 token，请求头带 `Authorization: Bearer <token>`）
- 各页面数据按当前用户展示

### 3.6 验收标准

- [ ] 注册两个用户 A、B
- [ ] A 登录只看到 A 的订单，B 登录只看到 B 的订单
- [ ] 未登录访问受保护接口返回 401
- [ ] 密码以哈希存储，数据库无明文

## 5. 迭代 3：订单号动态化 + 主动索取

### 5.1 产品需求（PRD）

**问题**：复杂售后固定查 O-001（`DEMO_ORDER_NO` 硬编码），用户下的任何单都查不到；订单号时间戳生成到秒有撞单风险。

**需求**：
1. 去掉 `DEMO_ORDER_NO` 硬编码
2. 从用户消息提取订单号
3. **用户没给订单号时，Agent 主动追问**（而不是瞎猜）
4. 订单号生成防撞单

### 5.2 实现技术

#### 5.2.1 订单号提取

```python
# 正则提取订单号（O- 开头 + 数字）
import re
def extract_order_no(text: str) -> str | None:
    m = re.search(r'O-[\d]+', text)
    return m.group() if m else None
```

#### 5.2.2 主动索取（核心：复用 interrupt 机制）

这是关键设计——**"信息不足就暂停追问，用户补充后恢复"**，和审批的 interrupt 是同一个机制：

```
分流 complex → 售后核实节点 → 没订单号？
  → interrupt 暂停，反问"请提供订单号"
  → 用户回答订单号 → resume 恢复 → 继续核实
```

```python
def aftersale_node(state):
    order_no = extract_order_no(state["messages"][-1].content)
    if order_no is None:
        # 没订单号 → 主动追问
        order_no = interrupt({"type": "ask_order_no", "prompt": "请提供订单号"})
    order_info = query_order(order_no)
    ...
```

#### 5.2.3 订单号生成防撞单

```python
# 加毫秒 + 随机数，避免同一秒撞单号
order_no = f"O-{datetime.now().strftime('%Y%m%d%H%M%S')}{random.randint(100, 999)}"
```

### 5.3 验收标准

- [ ] 用户消息带订单号 → 直接查该订单
- [ ] 用户消息没订单号 → Agent 反问"请提供订单号"
- [ ] 用户补充订单号 → 继续核实
- [ ] 同一秒下两单不撞单号

### 5.4 澄清流程设计（企业级）

订单号主动索取本质是**澄清流程**（信息不足就追问）的一个具体应用。本节把澄清流程的完整设计沉淀下来，供后续迭代复用。

#### 5.4.1 澄清的本质与类型

**澄清 = Agent 发现"信息不足/意图不确定"时，主动追问，补齐信息后再继续，而不是瞎猜。**

| 类型 | 信息缺口 | 例子 |
|---|---|---|
| **意图澄清** | 不知道用户想干嘛 | "你好" → "请问想咨询售前、故障还是退换货？" |
| **槽位澄清** | 缺关键参数 | "我要退货" → "请提供订单号" |
| **确认澄清** | 高风险操作需确认 | "确认删除该订单吗？" |

> 本迭代的"主动索取订单号"是**槽位澄清**。

#### 5.4.2 两种实现范式

**方案 A：interrupt 暂停-恢复**（复用审批机制，同 checkpoint 能力）：

```python
def clarify_node(state):
    if state.get("need_clarify"):
        answer = interrupt({"type": "clarify", "question": "请提供订单号"})
        return {"clarify_answer": answer}
```

- 优点：复用 checkpoint，澄清中途重启不丢状态
- 缺点：interrupt 是"暂停"，前端体验是"请求挂起"，较重

**方案 B：多轮对话（自然澄清）⭐ 企业更常用**：

```
轮1：用户"你好" → Agent"请问想咨询什么？"
轮2：用户"我要退货" → Agent"请提供订单号"
轮3：用户"O-001" → Agent 处理
```

不做 interrupt，就是普通多轮对话。**关键是要有「澄清状态」**，让 Agent 记住"我在等用户回答什么"：

```python
class CustomerServiceState(TypedDict):
    messages: Annotated[list, add_messages]
    pending_clarify: Optional[str]  # 当前在等用户补充什么（如"订单号"）
    clarify_count: int              # 已澄清次数（上限控制）
```

每轮路由时**先检查 pending_clarify**，有澄清上下文就优先处理澄清回答，而不是重新分类。

#### 5.4.3 企业级五道防线

| 防线 | 说明 |
|---|---|
| **澄清次数上限** | 最多追问 2 次，超了转人工，防死循环 |
| **澄清超时** | 用户长时间不回答，降级（默认建议/关闭会话） |
| **澄清用「选项」而非自由文本** | 给按钮选（如「售前/故障/退换货」），比打字准、体验好 |
| **降级链** | 澄清 1 次 → 澄清 2 次 → 转人工，每级有兜底 |
| **澄清记录** | 记日志：为何澄清、问什么、答什么、几次。频繁澄清 = 提示设计有问题 |

> ⭐ 关键洞察：澄清选项就是"给用户看的 enum"——和分流器的 `Literal` enum 同一个思想，收窄回答空间。

#### 5.4.4 落地演进

| 阶段 | 澄清能力 | 实现 |
|---|---|---|
| 当前 | 规则硬识别问候 | rule_triage 加 GREETINGS |
| 本迭代 | 槽位澄清（订单号） | 缺订单号时反问 |
| 后续 | 意图澄清（低置信度） | 替代"低置信度兜底 complex" |
| 最终 | 通用澄清框架 | 澄清状态 + 上限 + 降级 + 记录 |

> 关键：现在"低置信度兜底 complex"的 bug，根本解法是**用意图澄清替代**——不确定时不猜 complex，而是问用户。

## 6. 迭代 4：转人工（坐席接管）

### 6.1 产品需求（PRD）

**问题**：当前只有"审批"（坐席点按钮），没有"接管"（坐席替代 AI 继续对话）。

**需求**：
1. 用户请求转人工 → 进入待接管队列
2. 坐席接管 → 双向实时对话
3. 接管时交接完整上下文（AI 已核实信息 + 对话历史），用户不重复描述
4. 结束会话 / 转回 AI

### 6.2 实现技术

#### 6.2.1 待接管队列

```
用户请求转人工 → 写接管单（thread_id、用户诉求、AI 已核实信息）→ 进入队列
坐席在管理端看到待接管 → 接管
```

#### 6.2.2 实时对话（核心技术决策）

**坐席接管是"双向实时对话"**，和审批的"单向决策"不同，需要双向通信：

| 方案 | 优点 | 缺点 | 选择 |
|---|---|---|---|
| **WebSocket** | 双向实时、低延迟 | 复杂（连接管理、心跳、断线重连） | ⭐ 推荐 |
| SSE + 轮询 | 简单（复用现有） | 坐席发消息要另想办法，不优雅 | 次选 |

**推荐 WebSocket**，理由：坐席接管是"坐席发消息、用户收，用户发消息、坐席收"的双向实时场景，WebSocket 是标准方案。

#### 6.2.3 接管流程

```
用户："我要转人工"
  → 分流 complaint 或 AI 处理不了 → 写接管单 → 待接管队列
  → 坐席在管理端点"接管" → WebSocket 建立连接
  → 坐席和用户双向对话（坐席看到完整上下文）
  → 结束会话 / 转回 AI
```

### 6.3 验收标准

- [ ] 用户请求转人工 → 待接管队列出现
- [ ] 坐席接管 → 双向实时对话
- [ ] 坐席看到 AI 已核实的信息 + 对话历史（不重复描述）

## 7. 迭代 5：生产化收尾

### 7.1 会话管理

**需求**：用户能看到历史会话列表、开多个会话、会话归档。

**技术**：会话表（session_id、user_id、创建时间、摘要），前端会话列表页。

### 7.2 订单状态机

**需求**：订单状态流转（待处理 → 退换货中 → 已退换），可追溯。

**技术**：状态枚举 + 流转日志表，禁止非法流转。

### 7.3 安全加固

| 项 | 说明 |
|---|---|
| API 限流 | 防刷（slowapi 或中间件） |
| 敏感信息脱敏 | 手机号/地址展示脱敏 |
| 权限校验 | 所有接口校验 user_id 归属 |

### 7.4 可观测性

| 项 | 说明 |
|---|---|
| 完整 trace | 每次对话全链路（已用 trace_id，补可视化） |
| 指标监控 | 分流准确率、审批时长、转人工率 |
| 评测回归 | golden set 定期回归 |

## 8. 总结
