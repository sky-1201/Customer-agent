## 1. 产品概述

### 1.1 背景与问题

消费者在购买和使用笔记本电脑的过程中，会遇到售前咨询、故障诊断、退换货、投诉等各类问题。传统人工客服存在响应慢、知识不一致、重复劳动等问题；而单纯的"问答机器人"只能回答简单问题，无法真正"办成事"（完成退换货、解决复杂故障、处理投诉）。

### 1.2 产品定位

> **一个聚焦笔记本电脑售后的智能客服系统，能对"复杂售后"问题做多维度协同核实，并通过"人工审批/接管"实现人机协作闭环。**

一句话：**用户带着问题进来，能带着"解决了"的结果出去。**

### 1.3 核心价值

| 价值点 | 说明 |
|---|---|
| 办成事 | 不只是回答问题，而是完成退换货判断、故障诊断、投诉处理等实质服务 |
| 准确可信 | 复杂问题基于真实知识库（三包政策、产品文档）和真实订单数据做判断，结论可溯源 |
| 人机协作 | AI 处理简单问题，复杂/高风险问题流转给坐席，坐席审批/接管，AI 辅助人不替代人 |
| 可控兜底 | 涉及退款/换货等实质操作必须人工审批，AI 不会失控 |

### 1.4 业务目标（MVP）

1. 跑通"复杂售后"完整闭环（用户提问 → 多维度核实 → 结论 → 审批/转人工 → 解决）
2. 简单问题（FAQ、简单售前）能快速响应
3. 坐席能在管理端完成"审批"和"接管"两种人机协作
4. 知识库可维护（产品文档、三包政策、FAQ、故障说明）

## 2. 目标用户与角色

| 角色 | 说明 | 使用端 |
|---|---|---|
| **消费者（C 端用户）** | 购买/使用笔记本，遇到售前、售后、投诉问题的用户 | 客户端 |
| **坐席（人工客服）** | 处理 AI 无法解决或需审批/接管的问题 | 管理端 |
| **知识库管理员** | 维护产品文档、三包政策、FAQ、故障说明 | 管理端 |

> MVP 说明：客户端**无登录、单一用户视角**（不做多用户管理）；管理端坐席与知识库管理员为同一人，无需权限体系。

## 3. 核心原则（贯穿所有设计，后续功能冲突时以此为准）

> **P1：Agent 是主角，电商是脚手架。**
> 商品、下单、订单等功能，一律"够 Agent 用就好"，不做完整电商。任何功能若不能服务于 Agent 场景，MVP 不做。

> **P2：聚焦复杂售后，不平均用力。**
> 核心资源投入"复杂售后 + 投诉"场景。简单 FAQ / 简单售前做"够用"即可。

> **P3：AI 辅助人，不是替代人。**
> 涉及实质操作（退款、换货）或系统无法处理时，必须流转给人工。AI 负责"查证、判断、草拟"，人负责"决策、兜底"。

## 4. 核心场景（用户故事）

### 场景 1：简单 FAQ（快速通道）

> 用户："笔记本第一次开机要怎么激活系统？"

- **系统行为**：识别为简单 FAQ → 快速通道 → 基于知识库（FAQ）直接回答。
- **成功标准**：单轮回答正确，无需进入多维度核实，无需人工。

### 场景 2：简单售前（产品咨询 / 推荐）

> 用户："预算 5000，办公用，主要看视频偶尔剪点视频，推荐哪款？"

- **系统行为**：识别为售前咨询 → 结合商品库，给出推荐 + 理由。
- **成功标准**：能结合商品参数（十多种型号）给出有依据的推荐，支持追问。
- **边界**：MVP 阶段售前做"能答"，不做深度个性化推荐（不依赖用户画像）。

### 场景 3：复杂售后（故障诊断 + 三包退换货）⭐ 核心场景

> 用户（王先生）：「我 3 月买的笔记本，蓝屏修了两次了，现在又蓝屏，我要退货！」

- **系统行为**（完整流程）：
  1. **识别**：命中风险信号（反复/退款诉求/情绪），识别为"复杂售后"，进入协同处理。
  2. **多维核实**（并行）：技术诊断（同一故障？）、政策判断（三包适用？）、订单核实（过保？维修记录？）。
  3. **交叉核验**：综合三维度，判断"是否符合换货条件"，给出结论 + 置信度。
  4. **质量保障**：结构化约束从源头防幻觉——政策结论来自结构化查询、话术 prompt 约束、结构化输出防漏答。
  5. **人工审批**：因涉及"换货"（实质操作），暂停并流转到坐席审批。
  6. **坐席审批**：坐席看完整上下文 + 建议结论 + 草拟回复，一键"同意换货"。
  7. **回复用户**：告知结论 + 换货流程引导，生成换货工单。
- **成功标准**：三包条件核实正确、结论有政策依据可溯源、审批闭环完成、用户得到明确结果。

### 场景 4：投诉 / 升级

> 用户："你们售后太差了，修了两次还没好，我要投诉到 12315！"

- **系统行为**：识别为投诉（高风险）→ 先安抚情绪 → 核实情况 → **强制转人工**。
- **成功标准**：投诉不自动下结论，一律流转坐席；坐席接手时带上完整上下文。

### 场景 5：转人工闭环

> 用户："这个情况比较复杂，我要跟真人说。"

- **系统行为**：AI 将对话上下文、已核实信息、草拟建议一并流转坐席；坐席接管后直接对话；用户**无需重复描述**。
- **成功标准**：坐席接管时能看到完整上下文，能直接继续对话；用户有明确感知"已转人工"。

## 5. 界面与功能设计

### 5.1 客户端（3 个界面，无登录，单一用户）

#### 界面① 客服页 ⭐（客户端灵魂）

**定位**：用户与 AI 客服（或人工坐席）对话的主界面。

**页面结构**：对话区 + 输入框（[发送] [上传图片(P1)]）。

**四个设计点**：

| # | 设计点 | 方案 |
|---|---|---|
| ① | 处理状态提示 | **分步提示 + 展示当前工作的 Agent**。分两个层次：简单问题展示单个角色 Agent（`[售前 Agent] 处理中`）；复杂售后展示多个协同 Agent 并行打勾（`✓ 技术诊断 Agent / ✓ 政策 Agent / ○ 订单 Agent`） |
| ② | 信息卡片 | **结构化信息用卡片**（订单、商品规格、维修记录等固定字段）；开放性解释用文字 |
| ③ | 核实依据 | **结论 + 简短政策依据**（B 方案）。涉及权益判断（能否换货）时强制展示依据，依据原文必须从知识库真实取出，不可由 LLM 编造 |
| ④ | 审批/转人工体验 | (a) 审批等待：明确"等待人工审核" + 预计时间 + 结果自动推送；(b) 身份切换：系统提示"已转人工/已转回智能客服" + 真人/机器人标识区分，**绝不互相伪装** |

**验收标准**：能完成场景 1-5 的对话交互；处理进度、Agent 分工、依据可展示；转人工/审批状态清晰。

#### 界面② 商品页（数据底座）

**定位**：展示商品 + 极简下单，唯一目的是**给 Agent 提供真实订单数据**。

**商品数量**：十多种型号（具体型号待定）。

**商品字段**（服务售后 Agent，非卖货）：

| 字段 | 服务对象 |
|---|---|
| 名称/型号、价格 | 订单核实 |
| CPU、内存、硬盘、显卡、屏幕 | 技术诊断 |
| 商品类别（微型计算机） | 政策判断 |

**下单流程**：商品卡片 → [立即下单] → 生成订单 → 提示"下单成功，订单号 XXX"。

**明确不做**：购物车、支付、收货地址、库存扣减、销量评价。

#### 界面③ 我的订单

**定位**：让用户（演示者）看到"订单真实存在"，Agent 查的订单即此页面数据。

**列表字段**：订单号、商品、时间、金额、状态。

**详情**：完整订单信息 + **维修记录展示**（支撑"修两次"场景的可见证据）。

**订单状态**（3 个）：已完成 / 退换货中 / 已退换。

**维修记录**：预置构造数据，关联到订单，是"修两次可换货"核心场景成立的必要条件。

### 5.2 管理端（3 个界面，极简，承载 HITL）

**管理端设计理念**：坐席看的是「结论 + 依据」，不是「一堆对话」。AI 干脏活（查证/判断/草拟），人只做决策。

#### 界面④ 待审批队列 ⭐（HITL 灵魂）

**定位**：Agent 遇到需审批的操作（换货/退款）时，生成待审批任务，坐席审批。

**列表字段**：审批单号 / 类型（换货·退款）/ 诉求摘要 / 置信度 / 提交时间。**低置信度单子高亮标记（⚠️）**。

**详情页**（核心，坐席看"结论包"非原始对话）：

| 区块 | 内容 |
|---|---|
| 用户诉求 | 完整描述 |
| Agent 核实结果 | ✓ 技术诊断 / ✓ 政策判断 / ✓ 订单核实（三维度结论） |
| 建议结论 + 置信度 | Agent 的判断与把握 |
| 政策依据 | 可展开查看原文（可溯源） |
| 草拟回复 | 坐席可直接用的回复 |

**审批操作（3 个）**：批准 / 拒绝（填理由）/ 修改后批准（编辑草拟回复）。

**结果回传**：审批结果实时推送回用户客服页（用户无需刷新）。

#### 界面⑤ 知识库管理

**定位**：维护四类知识，是 Agent 的弹药库。

**四个 Tab**，两类查法（关键认知：知识库是"混合"的）：

| Tab | 知识类型 | 管理方式 | 检索方式 |
|---|---|---|---|
| 产品文档 | 商品规格（结构化字段） | 表单 | 精确查询 |
| 三包政策 ⭐ | 政策条款（结构化字段） | 表单（字段化） | 精确查询 + 规则判断 |
| FAQ | 问答对（非结构化） | 文本增删改查 | RAG 召回 |
| 故障说明 | 故障知识（非结构化） | 文本增删改查 | RAG 召回 |

**三包政策必须字段化**（整机保修期、主要部件保修期、主要部件清单、换货条件、退货条件、政策出处），不能用自由文本——这是"精确判断"的前提。

**明确不做**：版本管理、审批流、批量导入。

#### 界面⑥ 待接管队列（P1）

**定位**：HITL 第二种形态，坐席替代 AI 继续对话。

**触发条件**：用户主动要求 / AI 处理不了 / 投诉（强制）。

**列表字段**：会话号 / 诉求摘要 / 转人工原因 / 等待时间。投诉类 ⚠️ 标记。

**接管界面**（核心）：
- **AI 已核实的信息置顶**（订单/政策/技术结论）
- **完整对话历史**（可展开）
- **AI 草拟建议**（坐席可参考）
- 对话区 + 真人标识（坐席发言带真人标识，与 AI 区分）

**结束方式**：结束会话（归档）/ 交回 AI（转回智能客服）。

### 5.3 核心能力（Agent 引擎，产品视角描述）

| 能力 | 产品描述 | 对应场景 |
|---|---|---|
| **意图识别与分流** | 快速判断用户消息是"简单还是复杂/投诉"，简单走快速通道，复杂进入协同处理 | 所有场景入口 |
| **多维度协同核实** | 对复杂售后，同时核实技术、政策、订单三个维度 | 场景 3 |
| **交叉核验与决策** | 综合多维度结论，判断是否符合退换条件，给出结论 + 置信度 | 场景 3 |
| **质量保障** | 结构化约束从源头保障：政策结论来自结构化查询（防幻觉）、话术 prompt 约束、结构化输出防漏答 | 场景 3、4 |
| **人工审批/接管** | 实质操作或处理不了时，带完整上下文流转给坐席 | 场景 3、4、5 |
| **知识检索与溯源** | 回答基于真实知识库，结论可回溯到原文（结构化字段精确查询 / 非结构化 RAG 召回） | 所有场景 |
| **对话记忆** | 会话内上下文连贯；跨会话关联用户历史（订单、历史工单） | 所有场景 |

> ⚠️ 本节只描述"能力"，技术实现（框架、架构、多 Agent 编排方式）在《技术设计文档》中另行定义，本 PRD 不涉及。

## 6. 复杂售后完整闭环（端到端，MVP 验收以此为准）

```
用户（客户端）                    系统                   坐席（管理端）
     │                            │                         │
     ├─ 发送:"蓝屏修两次了,要退货" ──▶│                         │
     │                            ├─ 意图识别:复杂售后+风险信号 │
     │                            ├─ 并行多维核实:              │
     │                            │   技术诊断(同一故障?)       │
     │                            │   政策判断(三包适用?)       │
     │                            │   订单核实(过保?维修记录?)   │
     │                            ├─ 交叉核验:符合换货条件+置信度│
     │                            ├─ 质量保障:结构化约束防幻觉   │
     │◀─ 分步提示:"正在核实,请稍候" ──┤                         │
     │                            ├─ 因换货需审批 → 生成待审批任务│
     │                            │                         ├─ 收到待审批工单
     │                            │                         ├─ 查看完整上下文
     │                            │                         ├─ 点"同意换货"
     │                            │◀─ 审批结果 ──────────────┤
     │◀─ "符合换货条件,为您生成换货单" ┤                         │
     │                            ├─ 生成换货工单,归档          │
     │                            └─ 闭环结束                  │
```

**关键设计点**：
1. 三个维度并行核实、互不干扰（技术/政策/订单是三类不同知识/数据，分开查证再交叉核验）。
2. 结论可溯源（"符合换货条件"必须能指向三包条款原文）。
3. 涉及实质操作（换货）必审批（AI 只判断草拟，不可逆操作由人拍板）。
4. 坐席看"结论 + 依据"，一键审批，效率高于自己重查。

## 7. 数据需求

### 7.1 数据源与真实性

| 数据 | 来源 | 真实性 | 说明 |
|---|---|---|---|
| 产品规格参数 | 真实品牌官网（公开） | 真实 | 十多个型号的规格 |
| 三包政策 | 《微型计算机商品修理更换退货责任规定》（国家法规，公开） | 真实 | 字段化存储 |
| 故障知识 | 维修论坛、官方知识库、公开资料 | 真实（整理） | 关联商品型号 |
| FAQ | 公开常见问题 + 自整理 | 真实（整理） | 标准问答对 |
| 商品/订单 | 项目自建 | 构造 | 十多个商品，下单生成订单 |
| 维修记录 | 项目预置 | 构造 | 支撑"修两次换货"核心场景 |
| 用户对话 | 项目构造 | 构造 | 基于真实政策+真实商品，合理构造并标注 |

### 7.2 知识库的分类存储（重要）

知识库是"混合"的，两类知识两种查法：

| 类别 | 内容 | 查法 |
|---|---|---|
| **结构化**（字段明确） | 三包政策、商品规格、订单、维修记录 | 精确查询 + 规则判断 |
| **非结构化**（开放问答） | FAQ、故障说明 | 向量化 + RAG 召回 |

> **原则**：需要精确判断的（政策/规格）用结构化查询；需要语义匹配的（FAQ/故障）用 RAG。政策不能用 RAG——语义近似对政策判断是灾难（"修2次"≠"修3次"）。

### 7.3 关键原则

> **知识是硬的（真法规、真产品、真政策），对话是可控的（自己构造 + 标注）。**
> 任何演示结论必须能回溯到真实知识库原文；面试/评审时明确说明"哪些真实、哪些构造、为什么"。

## 8. 非功能需求

| 类别 | 需求 |
|---|---|
| **可靠性** | 复杂售后核实失败时，降级为转人工，不静默失败；涉及实质操作必须审批 |
| **可控性** | 单次对话有处理步数/时间上限，超限转人工；不会无限循环 |
| **可解释性** | 结论可溯源到知识库原文；坐席能看到 AI 判断依据，非黑盒 |
| **安全** | 敏感信息脱敏展示；AI 回复不承诺超出政策范围的赔偿 |
| **可观测性** | 每次对话、每个结论、每次审批可追溯（对话记录 + 处理日志） |
| **性能（MVP 参考）** | 简单问题秒回；复杂售后核实给明确等待提示，不阻塞 |

> MVP 阶段非功能需求从简，但"可控性、可解释性、可溯源"三条是硬性要求，不能砍。

## 9. 范围与优先级

| 优先级 | 内容 |
|---|---|
| **P0（MVP 必做）** | 界面①②③④⑤ + 核心能力（分流/协同核实/交叉核验/质检/知识检索） |
| **P1（进阶）** | 界面⑥ 待接管队列、图片识别（多模态）、坐席工作台完善 |
| **P2（可选）** | 情绪识别细化、数据看板、主动推荐营销 |

**MVP 验收一句话**：**场景 3（复杂售后）端到端闭环跑通，简单问题快速响应，坐席能审批（接管为 P1）。**
